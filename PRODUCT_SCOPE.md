# SerbisYO Product Scope

## 1. Hackathon Scope Rule

The team has only a few days to build, test, polish, and present the system. The goal is **not** to simulate a nationwide production platform. The goal is to demonstrate a complete and credible core experience.

The prototype should prioritize one full loop:

> **Discover a service -> understand what to expect -> view community intelligence -> contribute an experience -> update the service intelligence.**

## 2. Must-Have MVP

- Responsive web application for desktop and mobile.
- Map-based service discovery.
- Search establishments, organizations, offices, businesses, institutions, and eligible individual service providers.
- Display service locations through map markers.
- Basic service information:
  - Name
  - Category
  - Address/location
  - Operating hours
  - Open/closed status where practical
  - Available services
- Search result/service cards.
- Individual service profile page.
- Community service intelligence:
  - Average waiting time
  - Average processing/service time
  - Reliability/consistency
  - Information accuracy
  - Service quality
  - Accessibility
  - Overall community experience
- Peak/common busy hours if sample data can support it.
- Community contribution form.
- Contribution fields should include:
  - Service used
  - Visit date/time
  - Waiting time
  - Processing/service time
  - Whether the service was available
  - Whether posted information was accurate
  - Service quality rating
  - Accessibility rating
  - Overall experience
  - Optional comment
- Recent community contributions/experiences.
- Simple SerbisYO Score / Service Reliability Score.
- Simple Community Confidence indicator.
- Basic moderation/reporting path for incorrect or abusive information.

## 3. Should-Have Features

Implement only after the Must-Have flow works end to end.

- Filters:
  - Open now
  - Shortest waiting time
  - Highest reliability
  - Category
  - Accessibility
- Sorting nearby results.
- Save/favorite service.
- User contribution history.
- Suggest an update / report incorrect information.
- Simple service comparison.
- Basic waiting-time trend chart.
- Establishment response to feedback.
- Basic user authentication if it does not delay the core experience.

## 4. Future Scope / Not for the Main Hackathon Build

- Full provider account/profile-claiming workflow.
- Real-time queue system integration.
- Appointment or reservation booking.
- AI-generated recommendations.
- Complex predictive models.
- Full navigation/route optimization.
- Automated fraud detection.
- Large-scale verification system.
- Nationwide data ingestion.
- Dedicated native mobile application.
- Advanced provider analytics dashboard.
- Production-grade identity verification.
- Payment or transaction processing.

## 5. Non-Goals

SerbisYO is not primarily:

- A social network
- A generic review site
- A pure queueing application
- A booking platform
- A complaint portal
- A business directory with only addresses and star ratings
- A platform for rating arbitrary private individuals

## 6. Feature Freeze

Target feature freeze: **October 21, 2026** once the core MVP is functional.

After feature freeze:

- No new major features unless necessary to complete the core flow.
- Focus on bug fixing, responsiveness, data quality, demo preparation, and polish.
- Protect the presentation flow from late regressions.

## 7. Definition of Done for the Prototype

The prototype is considered demo-ready when:

- A user can open the app on desktop and mobile.
- A user can search or browse service providers on the map.
- A user can open a service profile.
- A user can understand key service intelligence without needing explanation from a developer.
- A user can submit a community experience.
- Submitted data can be represented in the service profile or demo state.
- The SerbisYO Score and confidence indicator are explainable.
- Core navigation has no blocking errors.
- The presentation team can complete the planned live demo in a few minutes.
